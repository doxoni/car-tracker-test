# Repository Guidelines

Руководство для контрибьюторов проекта учёта расходов по фурам (Telegram Mini App + бот + PostgreSQL в облаке).

## Структура проекта и организация модулей

- `app/` — Flask-приложение (Mini App и API):
  - `app/__init__.py` — создание приложения, blueprints, ожидание готовности БД.
  - `app/db_schema.py` — приведение схемы к актуальной (миграции alembic; при сбое — `db.create_all()`).
  - `app/db_retry.py` — повтор запроса к БД один раз, если база была «спящей».
  - `app/config.py` — конфиг из переменных окружения (`DATABASE_URL` / `DB_HOST`+... / SQLite), размер пула через `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`.
  - `app/models.py` — модели: `User`, `Vehicle`, `Expense`, `FuelBarrel`, а также `Driver`, `Customer`, `FuelEntry`, `ServiceEntry`, `Report` (сущности старой системы).
  - `app/auth.py` — авторизация по Telegram initData, уровни доступа 1/2/3.
  - `app/routes.py` — новый API (`/api/vehicles`, `/api/expenses`, `/api/barrels`, ...) и веб-маршруты Mini App (`/`, `/app`, `/new`, `/static/...`).
  - `app/legacy_routes.py` — API старой системы (`/api/cars`, `/api/drivers`, `/api/customers`, `/api/catalog`, `/api/barrel`, `/api/month-costs`, `/api/report-summary`, `/api/report`, `/api/reports`), который использует старая GUI.
  - `app/legacy_catalog.py` — каталог работ по обслуживанию (101 пункт, группа `service`).
  - `app/import_legacy.py` — импорт данных старой `cars.db` в новую базу.
- `app/import_wlp.py` — импорт машин из архива Wialon (`.wlp`): номер и марка из имени объекта.
  - `app/notifications.py` — отправка уведомлений в Telegram.
  - `app/main.py` — точка входа: веб-сервер + бот в отдельном потоке.
  - `app/bot_runner.py` — запуск бота в потоке (для gunicorn на Render).
- `bot/bot.py` — Telegram-бот на `python-telegram-bot` (long polling).
- `app/static/` — файлы Mini App: `index.html` — старая GUI (основная, её открывает бот по `/app`), `new.html` — новый интерфейс (доступен по `/new`), `css/` и `js/` — оформление нового интерфейса.
- `migrations/` — Alembic-миграции; `alembic.ini` в корне, адрес БД берётся из `DATABASE_URL`.
- `tests/test_app.py` — pytest-тесты на SQLite.
- `tests/test_import_legacy.py` — проверка импорта старой базы.
- `tests/test_legacy_routes.py` — проверка API старой системы.
- `tests/test_legacy_gui_contract.py` — сверка адресов, которые вызывает старая GUI, с серверными маршрутами.
- `wsgi.py` — точка входа для gunicorn (`wsgi:app`).

Скрипты эксплуатации:

- `setup_db.ps1` — создаёт облачную базу PostgreSQL. По умолчанию Neon (бесплатно навсегда, карта не нужна). Google Cloud SQL — только по явному ключу `-UseCloudSql`: бесплатного тарифа у Cloud SQL больше нет, есть лишь 30-дневный trial и $300 на 90 дней, дальше списание ~$15/мес, а с картой без денег аккаунт блокируют и базу удаляют. Сохраняет строку подключения в `.db_connection.txt` и применяет миграции.
- `setup_neon.py` — создаёт проект в Neon через API (нужен ключ в `neon_key.txt`).
- `apply_migrations.py` — применяет миграции alembic к базе из `.db_connection.txt`.
- `deploy_render.py` — создаёт/обновляет сервис на Render через API, ставит `DATABASE_URL`, запускает деплой.
- `setup_all.cmd` — одна команда: база + Render + админ.
- `create_admin.py` — создаёт админа в БД (уровень 1/2/3).
- `night_sleep.py` — усыпление и разбуживание сервиса на Render через API (suspend/resume).
- `import_wlp.cmd` — загрузить машины из архива Wialon (`.wlp`) в облачную базу:
  `.\import_wlp.cmd "C:\путь\Объекты (1).zip"`.
- `app/night_mode.py` — ночное окно 02:00-05:00 по Киеву (`is_night`, `night_info`).
- `set_level.cmd` — выдать уровень доступа без правки скриптов.

## Команды сборки, тестов и запуска

```powershell
python app/main.py                 # запуск веба + бота в одном процессе
pip install -r requirements.txt    # зависимости
python -m pytest tests/ -q        # тесты
.\setup_all.cmd 123456789         # создать облачную БД и задеплоить на Render
```

Одноразовые скрипты:

```powershell
python -m app.import_legacy --db "C:\path\cars.db"   # перенос старой базы в новую
python check_legacy_api.py --base http://127.0.0.1:5055   # сверка API с эталоном
```

Переменные окружения:

```powershell
$env:TELEGRAM_TOKEN="123:ABC"     # токен @BotFather
$env:DATABASE_URL="postgresql://..."  # строка подключения к облачной БД
```

## Уровни доступа

Уровни выдаёт бот (названия команд нестандартные - это и есть защита):
`/yuser_1` - 1 уровень (водитель), `/admunus2` - 2 уровень (оператор),
`/fraeadmin3` - 3 уровень (суперадмин), `/admin 1|2|3 add <user_id>` -
выдать уровень другому, `/admin list` - список. Вручную: `.\set_level.cmd <user_id> <уровень>`.

Права зависят от `OPEN_ACCESS`: при `OPEN_ACCESS=1` уровни не ограничивают
ничего, при `0` - 1 уровень видит только активные фуры и свои расходы,
2 уровень управляет фурами и бочками, 3 уровень - админка и логи.

## Ночная пауза 02:00-05:00 по Киеву

Ночью бот Telegram не отвечает и сам поднимается в 05:00: окно проверяется
в `ensure_bot_started`, а сторож в `app/bot_runner.py` каждые 30 секунд
останавливает опрос и поднимает бота. Состояние окна видно в `/api/health`
в блоке `night`. Настройки: `NIGHT_MODE_ENABLED`, `NIGHT_START_HOUR`,
`NIGHT_END_HOUR`, `NIGHT_TZ`.

### Сон всего сервиса (suspend/resume)

Ночью усыпляется не только бот, а весь сервис на Render: `suspend` через
Render API полностью останавливает контейнер (любой запрос отдаёт 503,
сам сервис не поднимается), `resume` поднимает его за ~30 секунд.

Это возможно только явной командой API: у сервиса включён health check
`/api/health`, и сам Render стучится в него постоянно, поэтому от простоя
сервис не засыпает.

Скрипт `night_sleep.py`:

| Команда | Что делает |
| --- | --- |
| `suspend` | Усыпить сервис. Если в ветке есть незадеплоенный коммит - не усыпляет (Render не деплоит в усыпленном состоянии). |
| `resume` | Разбудить сервис и дождаться ответа `/api/health`. |
| `wait_until_morning` | Дождаться 05:00 по Киеву и разбудить сервис. |
| `auto` | Сам решает по киевскому времени и по состоянию сервиса: ночью усыпляет, днём разбужает. |
| `status` | Показать время и состояние сервиса. |

Ключ Render API: переменная окружения `RENDER_API_KEY` или файл
`render_key.txt` (не в Git).

### Workflow-файлы GitHub Actions

- `.github/workflows/night-sleep.yml` - раз в 15 минут вызывает `night_sleep.py auto`.
- `.github/workflows/keepalive.yml` - раз в 10 минут пингует `/api/health`, чтобы днём сервис не уснул от простоя. Ночью (с 01:45 до 05:00 по Киеву) пинг пропускается, а вместо него сервис будится через `night_sleep.py resume`.

Почему cron частый, а не точно в 02:00 и 05:00: запланированные запуски
Actions опаздывают на часы. Команда `auto` смотрит на реальное состояние
сервиса, поэтому любой запуск в любое время оставляет его в правильном
состоянии. Расписание считается по UTC, а решение принимается по
`TZ=Europe/Kyiv` - смена летнего времени ничего не ломает.

### Правило о workflow-файлах

Файлы `.github/workflows/*.yml` GitHub не примет без scope `workflow` у
токена: push будет отклонён. Содержимое workflow менять через REST API
нельзя (тот же scope), а вот включить/выключить workflow через
`PUT .../actions/workflows/<file>/enable` можно - это используется как
запасной вариант, если ночной workflow мешает.

## Стиль кода и соглашения по именам

- Python 3, 4 пробела, `snake_case` для функций и переменных, `UPPER_CASE` для констант (`TELEGRAM_TOKEN`, `SERVICE_NAME`).
- Обязательная шапка-комментарий с `# -*- coding: utf-8 -*-` и русским docstring, где указан запуск.
- Пользовательские строки, ключи JSON и комментарии — на русском; имена полей моделей менять нельзя, это схема БД.
- Секции разделяйте комментариями-баннерами вида `# ---------- Описание ----------`.
- Форматирование: код в стиле `black`, отступы 4, без табов; линтеры в проекте не настроены.

## Тестирование

Автотесты есть: `python -m pytest tests/ -q`. Проверяются health-check, отдача Mini App, 401 без авторизации и работа дашборда под тестовым пользователем.

## Старая GUI и совместимый API

Основной интерфейс Mini App - старый (`app/static/index.html`). Он работает поверх
совместимого API в `app/legacy_routes.py`, который повторяет контракт старого
проекта: ответы вида `{ok: true, ...}` или `{ok: false, error: "..."}`, адреса
`/api/cars`, `/api/cars/<id>/fuel`, `/api/cars/<id>/services`, `/api/drivers`,
`/api/customers`, `/api/catalog`, `/api/barrel`, `/api/month-costs`,
`/api/report-summary`, `/api/report` (текстовый файл), `/api/reports`.

Важно:

- Названия blueprint и его маршрутов менять нельзя - GUI завязана на эти адреса.
- Каталог работ лежит в `app/legacy_catalog.py` (список, не база).
- Уровни доступа в старой системе: 2 - бочка, 3 - отчёты.
- Проверка совместимости: `python check_legacy_api.py --base http://127.0.0.1:5055`
  (эталон - старый проект на порту 8000) и `tests/test_legacy_gui_contract.py`.

### Бочка: как переводить старые действия

В старой системе запись бочки - это действие, а не «наполнение»:

| Действие | Что значит | Куда в новой базе |
| --- | --- | --- |
| `add` | долили бочку | `fuel_inflow` (остаток растёт) |
| `fill` | заправили машину из бочки | `fuel_outflow` с машиной (остаток падает) |
| `sub` | убавили | `fuel_outflow` без машины (остаток падает) |

Остаток = долили минус заправили минус убавили, поэтому может быть
отрицательным - так же, как в старом учёте.

### Старая cars.db синхронизируется с облаком

`cars.db` - не эталон, а локальная копия облачной базы старой системы:
записи приходят и удаляются при синхронизации. Поэтому перед импортом
(`python -m app.import_legacy`) базу нужно обновить синхронизацией, иначе
в новую базу попадут уже удалённые расходы и услуги.

## Коммиты и Pull Request

Сообщения — короткие, в стиле Imperative Mood: `Добавь историю работ по авто`. В Pull Request указывайте: что изменено, как проверить, какие файлы затронуты. Скриншоты нужны только для изменений UI бота.

## Безопасность и конфигурация

- Токен бота храните только в переменной окружения `TELEGRAM_TOKEN` или в `render_env.txt` (файл в `.gitignore`).
- Render API-ключ — в `render_key.txt` (тоже в `.gitignore`).
- Никогда не коммитьте токены, пароли и рабочую базу (`*.db`).
- Схема БД меняется через миграцию Alembic (`ALTER TABLE` с проверкой существования колонки), чтобы не сломать существующую базу. Новую колонку с `NOT NULL` сначала добавлять со `server_default`, потом заполнять данные, потом значение по умолчанию убирать.
- Ограничения в миграциях называем явно: `batch_alter_table` пересоздаёт таблицу на SQLite и безымянные ограничения туда не переносит.
- Номера машин и пробеги — личные данные: не выводить их в логи и консоль.
